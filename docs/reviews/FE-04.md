## Findings

### Blockers

1. **Open redirect through `?next=`.** `safeNext` in `components/auth/login-flow.tsx:14` accepts any value that starts with `/` and not `//`. But `/\evil.com` passes that check and browsers resolve it to `https://evil.com/`: `new URL('/\\evil.com', 'https://doqto.in').href === 'https://evil.com/'`.
   - Why it matters: an attacker can send a real Doqto login link that drops the patient on a look-alike page right after a genuine login, which is the classic phishing setup.
   - Fix: resolve and compare origins, for example `const u = new URL(next, location.origin); return u.origin === location.origin ? u.pathname + u.search + u.hash : null`, or also reject `\` and control characters.
   - Add test cases for `/\evil.com`, `/\/evil.com`, `//evil.com` and `https://evil.com`.

### Should fix

None.

### Nits

1. New users land on `/profile?welcome=1` to add a name. Consider letting them skip, so a patient who only wants to check a doctor's status is not stopped.

**Verdict: Changes requested.** 1 blocker remains (Blocker 1, still open by another route). The real-API criterion now holds.

**Blocker 1 (open redirect): partly fixed, still open.** `safeNext` (`components/auth/login-flow.tsx:17-25`) now resolves `next` with `new URL(next, origin)` and keeps it only when the origin is unchanged. But it returns `url.pathname + url.search + url.hash`, and the *normalised* pathname can itself start with `//`. The caller then passes that string to `router.replace` (`login-flow.tsx:70-75`), which resolves it again as a protocol-relative URL. Next 16.4's router treats a different origin as an external URL and does a full navigation (`app-router-utils.js` `isExternalURL`, `navigate-reducer.js:10`).

Tested with the shipped function body in Node (WHATWG `URL`), origin `https://doqto.in`:

| `next` | `safeNext` returns | Where the router lands |
| --- | --- | --- |
| `/\evil.com`, `/\/evil.com`, `//evil.com`, `https://evil.com`, `javascript:alert(1)`, `\\evil.com` | `null` | `/` (safe) |
| `/\t/evil.com`, `/\n/evil.com`, `/\r\n/evil.com`, `\t//evil.com` | `null` | `/` (safe) |
| `/%5C%5Cevil.com`, `/%2F%2Fevil.com` | same string | on-site, as a literal path (safe) |
| `/foo?x=1#h` | `/foo?x=1#h` | allowed, as expected |
| **`/.//evil.com`**, **`/..//evil.com`**, **`/a/..//evil.com`**, **`/%2e//evil.com`**, **`/./\evil.com`** | **`//evil.com`** | **`https://evil.com/`** |

- Who it affects: a returning user goes straight to `next` and is redirected off-site. For a new user, `next` is passed through `encodeURIComponent` to `/profile?welcome=1&next=...`. `profile-view.tsx:87` runs `safeNext('//evil.com')` on that, which returns `null`, so new users are safe today by accident.
- This is RD's fault too: the round-1 fix suggestion had the same gap. Sorry.
- Fix: after the origin check, reject a result whose pathname starts with `//` or `/\`. Simplest:

  ```ts
  if (url.origin !== origin || url.pathname.startsWith('//')) return null;
  ```

  `URL` has already turned `\` into `/`. Another option is to return `url.href`: the same-origin absolute URL cannot be re-read as another host.
- Add test cases to `login-flow.test.tsx:98-115` for `/.//evil.com`, `/..//evil.com` and `/%2e//evil.com`. A test that resolves the *returned* value against the origin and asserts the origin is unchanged would catch this whole class of bypass.
- The new tests (`login-flow.test.tsx:98-115`) cover the round-1 cases. `/%5Cevil.com` staying on-site as a literal path is correct.
