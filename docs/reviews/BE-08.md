## Findings

### Blockers

None.

### Should fix

1. **Users created by "add staff" never go through first-login setup, and lose every role on removal.** `addStaff` inserts the user with `$addToSet: { roles: 'clinic_staff' }` and `$setOnInsert` without `roles: ['patient']`, `phoneVerifiedAt`, `language` or a `consentLog` entry (`clinics.service.ts:150-166`). `upsertOnLogin` sets all of those only on insert (`users.service.ts:59-73`). The comment at `clinics.service.ts:155`, "Consent is captured when they first log in themselves", is therefore not true. Failure scenarios (probe):
   - The receptionist logs in for the first time and gets `isNewUser: false`. FE skips the new-user consent step, so `whatsappOptIn` stays false and `consentLog` stays empty for good. They never get the WhatsApp alerts staff rely on, and there is no record that they were asked (checklist L, consent "where data is first collected").
   - They have no `patient` role, so once patient routes use `@Roles('patient')` they cannot book for themselves on the same number.
   - After removal from their last clinic, `roles` is `[]` (`:218-220`). That is a logged-in account with no role at all.
   - A doctor can also create an account (phone + a name of the doctor's choice) for anyone, with no notice to that person. That is acceptable for a pilot, but it should be stated.
   - Fix:
     - Insert with `roles: ['patient', 'clinic_staff']` (use `$setOnInsert` for `patient` and `$addToSet` for the existing-user case; they cannot both touch `roles`, so do two updates or a pipeline update).
     - Have `upsertOnLogin` treat "no `phoneVerifiedAt`" as a first login. Set `phoneVerifiedAt`, write the consent row and return `isNewUser: true`.
     - Drop the role with one conditional update, `updateOne({ _id: uid, clinicIds: { $size: 0 } }, { $pull: { roles: 'clinic_staff' } })`. The current read-then-write (`:215-220`) can remove the role just after a concurrent add at another clinic.
     - Add an e2e for the first login of a staff-created user.
2. **Clinic create can leave the two lists out of sync.** `clinics.create` (`:61-69`) and then `doctor.clinicIds.push` + `saveWithListing` (`:71-72`) are separate writes. If the second one throws, the clinic exists with `doctorIds: [doctor]` and `ownerUserId`, but the doctor does not list it. For example, a slug 11000 race with a same-name doctor in the same city (BE-07 Nit 1), or the version conflict BE-09's fix will introduce. The clinic then appears in `/clinics/mine` and grants `manage`, but not on the profile or in search, and a retry creates a duplicate. Fix: on failure, delete the clinic (compensating write), or `$addToSet` the clinic id onto the doctor with a plain atomic update first and only then recompute listing. Transactions are not needed (DB doc section 5 keeps them for payments and reviews).
3. **`/geo/geocode` lets any logged-in user fill the shared Nominatim queue.** The route is open to every logged-in user (`geo.controller.ts:15-23`, `CONTRACT.md:109`). Accounts cost one OTP. The limit is 30 per minute per IP (`:16`). The live provider sends one request every 1.1 s for the whole process and queues the rest with no cap (`nominatim-geocoder.provider.ts:80-85`). There is no money cost (Nominatim is free), but the capacity is shared. Failure scenarios:
   - Two clients on different IPs each sending 30 uncached queries a minute (about 60 a minute, above the provider's roughly 54 a minute) make the queue grow without bound. A doctor filling in the clinic form waits longer and longer for pins, and requests pile up in memory.
   - Sustained load breaks the Nominatim usage policy, and an IP or User-Agent ban stops geocoding for every clinic.
   - Fix:
     - BE: allow only callers with a doctor profile or `clinic_staff` (the only users of the clinic form). Use a per-user throttler key (`req.user.id`) instead of the IP.
     - INT: bound the wait in `waitForSlot`. Return `[]` ("place the pin by hand") when the wait would be over about 5 s (see Requests).
4. **`null` for `name` or `address` on `PATCH /clinics/:id` returns 500, and the DTO parity spec does not exist.** `UpdateClinicDto` uses `@IsOptional()` (`dto/clinic.dto.ts:65`, `:72-75`), which lets `null` through. The Zod schema rejects it. `c.name = null` / `c.set('address', null)` then fails Mongoose validation (probe: 500). The comment at `dto/clinic.dto.ts:26` says `clinic-dto-parity.spec.ts` checks the mirror, but that file does not exist. This is the same issue as BE-07 Should fix 1, and has the same fix. Use `ValidateIf(v !== undefined)` for non-nullable fields, and add the parity spec with `null` cases.

### Nits

1. **There is no way to link a second doctor, so the `doctorIds` branch of the guard is untested.** `resolveClinicAccess` gives `manage` to any doctor in `doctorIds` (`clinic-scope.guard.ts:53-54`). Only `create` ever writes `doctorIds`. When a "link doctor" route lands, add the e2e for a linked doctor who is not the owner. Also add the admin case (403, probe) to "scopes every clinic route by role".
2. **Photo count and photo delete are not atomic.** `addPhoto` checks `photos.length` on the loaded document (`clinics.service.ts:117`), so two uploads in parallel can exceed `CLINIC_PHOTOS_MAX`. `DELETE /photos/:index` (`:136-142`) can remove the wrong photo if two managers delete at the same time. Use `$push` with a `photos.<max-1>: { $exists: false }` condition, and delete by `key` instead of index (a contract change, so for FE-06 it is cheaper now than later).
3. **`assertManage` runs after multer.** On `POST /:id/photos` (`clinics.controller.ts:71-83`), a read-only staff member's 2 MB upload is buffered before the 403. Harmless, but a `ClinicManageGuard` (or a `requireManage` flag on `ClinicScopeGuard`) would reject before the body is read and remove the five `assertManage` calls.
4. 404 for an unknown clinic and 403 for someone else's clinic (`clinic-scope.guard.ts:34-39`) tells a logged-in user which clinic ids exist. Ids are ObjectIds and clinics are public through search, so this is fine. Write it down so the same pattern is not copied to appointments, where 404 for both is the rule (checklist D, "other clinic gets 403/404").
