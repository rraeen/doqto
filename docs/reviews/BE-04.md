Security points checked, all holding:

- **No plain OTP stored or logged.** The provider returns only `codeHash` (`integrations/otp/otp.provider.ts` `OtpChallenge`). Delivery errors are logged through `scrubPersonalData` (`auth.service.ts:80-82`).
- **OTPs never go through the notifications outbox.** `grep -rn otp apps/api/src/notifications` finds nothing. Delivery goes through `OtpProvider` directly, as settled in INT-02 should-fix 1.
- **OTPs are single use.** The row is deleted with `{ _id, codeHash }` before the user is upserted (`auth.service.ts:146-149`). A request for a new code that lands mid-verify changes `codeHash`, so the old verify gets `OTP_EXPIRED`. This closes the INT-02 "Notes for later reviews" BE-04 item: consume on success, atomic `$inc`, replace the row on a new request.
- **No enumeration.** `otp/request` returns the same `{ expiresAt, channel }` for new and existing phones (probe). The only difference is the message language. `isNewUser` and `ACCOUNT_SUSPENDED` appear only after a correct code.
- **JWT algorithm pinned.** `HS256` is pinned at sign and verify (`auth.module.ts:22-24`, `jwt-auth.guard.ts:44`). The secret must be at least 32 characters (`env.ts:56`). Probe: tokens with `alg: none`, or HS384/HS512 signed with the real secret, get 401 on `/me`. HS256 gets 200.
- **Suspended users.** They get `ACCOUNT_SUSPENDED` on verify (`auth.service.ts:154`), on refresh (the family is revoked, `token.service.ts:58-62`) and on `/me` (e2e). Other routes trust the JWT for up to 15 minutes, as `jwt-auth.guard.ts` documents.
- **Cookies.** The probe saw `doqto_at` with `Path=/; HttpOnly; SameSite=Lax` and `doqto_rt` with `Path=/api/v1/auth; HttpOnly; SameSite=Lax`, both host-only because `COOKIE_DOMAIN` is unset. `Secure` is set when `API_PUBLIC_URL` is https (`app-config.service.ts:23-25`). This matches INT-05 round 2 (host-only demo cookies, same-origin through the web rewrite, `SameSite=Lax`). Failed refreshes clear the cookies.
- **Demo flag and consent.** `isDemo` comes from `PROVIDER_MODE` (`users.service.ts:71`). WhatsApp consent is logged with `WHATSAPP_CONSENT_VERSION` at signup, and on every change through `PATCH /me` (`users.service.ts:67-69,120-128`; e2e). Opt-in defaults to true, as DB doc 3.1 and TDD 452 say.
- **No `Demo*` class imported outside `integrations/`** (grep). `channel: 'demo'` is read from `otp.mode` (`auth.service.ts:106`). That only labels the response and does not change behaviour.
- **Contract parity.** `contract-parity.spec.ts` checks that the DTOs accept and reject the same bodies as the Zod schemas. Error codes match `CONTRACT.md`, apart from Nits 2 and 3.

## Findings

### Blockers

1. **The global `JwtAuthGuard` returns 401 to anonymous callers on INT's payment webhook and demo file serving.** `AuthModule` registers `JwtAuthGuard` as `APP_GUARD` (`auth.module.ts:32`), so every route outside `@Public()` now needs a token. `IntegrationsModule.forRoot()` registers `PaymentWebhooksController` (`integrations/payment/payment-webhooks.controller.ts:25`) and `DemoStorageController` (`integrations/storage/demo-storage.controller.ts:28`), and neither is public. Probe results with no token:
   - `GET /api/v1/demo-storage/public/doctors/x.jpg` returns **401 `UNAUTHENTICATED`**. Expected: 404 for a missing file, or the file.
   - `POST /api/v1/webhooks/payments` returns **401 `UNAUTHENTICATED`** from the guard. The controller's signature check never runs.
   - Failure scenarios:
     - In demo, every doctor and clinic photo on the public search and profile pages (BE-07/BE-10, served from `demo-storage/public/...`) is a broken image for logged-out visitors.
     - The admin's 5-minute signed link to a registration scan does not work either. Demo cookies are host-only on the web origin, so they are never sent to the API host the URL points to. This breaks INT-06's "demo adapter keeps working with local files".
     - In live mode, every Razorpay webhook is refused, so no payment could ever confirm. This breaks the route INT-12 and INT-14 rely on.
   - Fix: both controllers need `@Public()`. They are INT's files, but BE owns the decorator and the guard. BE should export `Public` from somewhere INT may import (for example `apps/api/src/common/http/public.ts`, or re-export it from `auth/decorators`) and tell INT. INT then adds it to both controllers (see Requests).
   - BE should also add an e2e test that lists every route through Nest's router or Swagger and asserts that the routes reachable without a token are exactly this allowlist: `health`, `auth/*`, `GET /doctors`, `GET /doctors/:slug`, `webhooks/*`, `demo-storage/*`. That catches both missing and accidental `@Public()` in later stories.

### Should fix

1. **The verify limit and the global throttler ignore `CLIENT_IP_HEADER`.** `otp/request` keys on `clientIp()` (`auth.controller.ts:64`). The `@Throttle` on verify (`auth.controller.ts:70`) and the global `ThrottlerGuard` (`app.module.ts:64`) use the stock tracker, which is `req.ip`.
   - Probe with `CLIENT_IP_HEADER=cf-connecting-ip` and `TRUST_PROXY=0`: 22 verifies from 22 different `cf-connecting-ip` addresses gave 20 × 400 and then **429, 429**. Behind Cloudflare configured that way, the 21st patient in any 10-minute window cannot log in, which is BE-01 should-fix 1 again.
   - Fix: subclass `ThrottlerGuard` and override `getTracker` to return `clientIp(req, config)`, so there is one IP rule everywhere. Alternatively drop `CLIENT_IP_HEADER` and rely on `TRUST_PROXY`, which is what `infra/ENVIRONMENTS.md` documents (`2` for Cloudflare + Render).
   - Either way, note in the status file that `CLIENT_IP_HEADER` (like `TRUST_PROXY=2`) is spoofable while the Render origin (`*.onrender.com`) still accepts direct traffic. An attacker can then rotate the header to defeat the per-IP OTP limit, which is the SMS-pumping guard. INT-11 must lock the origin to Cloudflare before either is used.
2. **Two tabs that refresh at once log the user out.** Probe: two parallel `POST /auth/refresh` calls with the same `doqto_rt` cookie gave 200 and 401. The winner's new refresh token then also gave **401**, because the loser counts as reuse and revokes the family (`token.service.ts:71-74`). The loser's response also clears the cookies (`auth.controller.ts:104`), and that can arrive after the winner's `Set-Cookie`. On the web this is a normal event, not an attack: two open tabs, or TanStack Query firing several requests that each see 401 after the 15-minute access token expires.
   - Fix (BE): allow a short grace window, for example 10 to 20 seconds. Within that window, a token that was revoked by rotation (it has `replacedBy`) and is presented again gets 401 `REFRESH_INVALID` **without** revoking the family and **without** clearing cookies, so the winning tab's cookie stands. Outside the window, keep today's family revocation.
   - Also state the single-flight expectation in `CONTRACT.md` under `POST /auth/refresh`. The FE side is under Requests.
3. **`.env.example` does not list `CLIENT_IP_HEADER`** (checklist M), and `infra/ENVIRONMENTS.md` has no row for it. INT owns both files (see Requests). BE should add the request to its status file.

### Nits

1. `requestOtp` sends the code before upserting the row (`auth.service.ts:78-103`). If the upsert fails, the patient gets a code that can never work, and the per-phone quota is spent. Upserting first would avoid that, but it needs the challenge first, so a comment is enough.
2. The 429 from `otp/request` carries `details.retryAfterSeconds` but no `Retry-After` header (probe: header undefined). `CONTRACT.md` says RATE_LIMITED also sends the header. Either set it in `AppException.rateLimited`, or reword the contract line.
3. `PATCH /me` can return `ACCOUNT_SUSPENDED` (`users.service.ts:117`), but `CONTRACT.md` lists only `VALIDATION_FAILED` and `UNAUTHENTICATED` there. OTP delivery failure returns 503 with code `INTERNAL` (`auth.service.ts:83-87`), and that is not in the contract either.
4. Privacy-policy acceptance is not written to `consentLog`. DB doc 3.1 says `consentLog` holds "privacy policy / WhatsApp consent versions". Only WhatsApp is logged today. Fine for this story's criteria; log a follow-up (BE + FE-04 checkbox text).
5. A login by a `deleted` user gets `ACCOUNT_SUSPENDED` after the OTP is consumed and `lastLoginAt` is bumped (`users.service.ts:59-60`). BE-42 (account deletion) must decide whether a deleted phone can sign up again.
6. The throttler storage is in-memory, so OTP limits reset on restart and multiply with instances. That is fine on one Render instance. Revisit if the API ever scales out.
7. `scrubPersonalData` also redacts dates (`2026-10-10`) and years in log text. Erring safe is right; it only makes some 5xx logs harder to read.
8. `packages/shared/package.json` is still `"version": "0.1.0"`, while `CONTRACT_VERSION` is `1.0.0` and the changelog lists 0.2.0. Bump it or say the package version is not used.
9. The comment at `auth.dto.ts:16` points to `auth.dto.spec.ts`. The file is `contract-parity.spec.ts`.

## Requests to other workstreams

- **To INT:**
  - Add `@Public()` to `PaymentWebhooksController` and `DemoStorageController` once BE says where to import it from (Blocker 1).
  - Add `CLIENT_IP_HEADER` to `.env.example` and `infra/ENVIRONMENTS.md`, with the spoofing caveat (Should fix 1 and 3).
  - Demo: with the Vercel rewrite in front of Render, `TRUST_PROXY=1` probably makes `req.ip` a Vercel edge address. With 3 OTP requests per 10 minutes per IP, a handful of demo testers would then lock each other out. Check this as soon as the demo is deployed (it was already noted in INT-05 round 2, but with BE-04's limits it now matters).
- **To FE (FE-04 real-API check):**
  - Call the API same-origin as `/api/v1/...` through the Next.js rewrite, with `credentials: 'include'`, never an absolute cross-site `NEXT_PUBLIC_API_URL`. `doqto_rt` has `Path=/api/v1/auth` and both cookies are host-only `SameSite=Lax`.
  - Web never gets tokens in JSON. Do not send `X-Doqto-Client`. `otp/verify` and `refresh` return only `accessTokenExpiresAt` and `refreshTokenExpiresAt` (plus `user` and `isNewUser` on verify).
  - On 401 `UNAUTHENTICATED`, `POST /api/v1/auth/refresh` with body `{}` and retry once. On `REFRESH_INVALID` or `ACCOUNT_SUSPENDED`, go to login.
  - Make refresh single-flight: one in-flight promise per tab, and `navigator.locks` (Web Locks) across tabs. Until BE adds the grace window, a parallel refresh logs the user out (Should fix 2).
  - Send `whatsappOptIn` from the signup checkbox on `otp/verify` (default `true`). Branch on `isNewUser` for onboarding. `otp/request` returns `channel: 'demo'` in demo mode, which is when the `123456` hint shows.
  - Error codes: `OTP_INVALID` (`details.attemptsLeft`), `OTP_EXPIRED`, `OTP_LOCKED` (request a new code), `RATE_LIMITED` (`details.retryAfterSeconds`).
  - Logout is `POST /api/v1/auth/logout` with `{}` and returns 204.
- **To the coordinator:** INT-06 and INT-12 are Done, but this regression (Blocker 1) breaks them until both BE and INT land their parts.
