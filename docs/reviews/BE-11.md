## Findings

### Blockers

None.

### Should fix

1. **Schedules (BACKLOG criterion) are not seeded yet.** Failure scenario: from sprint 3, FE-11 and the booking and queue flows open on the demo with five listed doctors who have no schedule, so there are no free slots to book. Owner: **BE, with BE-14** (the first story with a schedule API). Extend `seedDemo` with one weekly schedule per doctor-clinic pair (DB doc 3.4) and keep it idempotent on the unique `{ doctorId, clinicId }`. Add a line to the BE status file, so the deferral is not tracked only in the `demo-seed.ts:4` comment. TDD 13 also lists sample appointments and a few reviews; those belong to the stories that create those collections (row 31).
2. **The safety check runs after the app boots, and the seed does not require demo mode.** `seed-demo.ts:265` boots the whole `AppModule`, which connects to Mongo and runs every pending migration in `onApplicationBootstrap` (plus `autoIndex`/`autoCreate` when `NODE_ENV` is not production). Only then does `assertSeedTarget` run (`:268`). Two failure scenarios:
   - `PROVIDER_MODE=live MONGODB_DB_NAME=doqto_prod pnpm seed:demo` is refused, but only after it has run migrations and index builds against the production database. No seed rows are written.
   - `PROVIDER_MODE=live MONGODB_DB_NAME=doqto_demo` passes. Live mode has no database-name rule (`provider-safety.ts:56-61`), so seeded accounts with `whatsappOptIn: true` (Should fix 4) sit behind live WhatsApp and SMS providers.
   - Fix: check `process.env.MONGODB_DB_NAME` (and the database in `MONGODB_URI`, as `providerSafetyProblems` does) **and** `PROVIDER_MODE === 'demo'` before `NestFactory`. Also check inside `seedDemo` with the real connection name (`users.db.name`), so every caller, including future e2e or scripts, is covered. Extend `demo-seed.spec.ts` with the live-mode case.
3. **The seed crashes if a seed slug is already taken** (probe D). `demo-seed.ts:125-129` has its own `slugify` and `$set`s that slug (`:202,236`) without checking for collisions. Failure scenario: someone tries demo onboarding as "Anita Sharma" with a Bareilly clinic (the DB doc's own example slug) and gets listed. Every later `pnpm seed:demo` then fails with E11000 halfway through, after clinics and staff have been written, and keeps failing. Fix: use `baseSlug` + `uniqueSlug` from `doctors/slug.ts`, excluding the seed doctor's own `_id` (as `saveWithListing` does), so there is one slug rule.
4. **Seeded users are opted in to WhatsApp with no consent record, on real-format numbers.** `demo-seed.ts:149` sets `whatsappOptIn: true` but writes no `consentLog` entry. BE-04 writes one, with `WHATSAPP_CONSENT_VERSION`, for every real opt-in. The phones `+91 90000 000xx` match `PHONE_E164_IN_REGEX` and fall in an allocatable mobile series (India has no reserved fictional range), so they may belong to real people. Today nothing is sent in demo mode (TDD 13). Combined with Should fix 2, though, a live provider could message them. Fix: seed `whatsappOptIn: false` (or add a matching `consentLog` entry), and keep the comment at `:8` saying the numbers are demo-only placeholders.
5. **The demo admin is publicly reachable.** In demo mode any phone logs in with `123456` (TDD 13). The admin phone is fixed in the source (`demo-seed.ts:18`), so anyone who reads the repo, or a guide that quotes it, becomes admin on the demo deployment. The admin detail returns signed URLs of registration scans (`admin-doctors.service.ts:114-116`). Real doctors invited to try demo onboarding (TDD 13 outreach) may upload their real certificates there. Checklist E ("credential scans ... only to admins") still holds technically, so this is not a blocker. Fix until Raunak decides (row 30): read the admin phone from an env var (for example `DEMO_ADMIN_PHONE`, in `.env.example` with no value), skip the admin when it is unset, and have the demo onboarding copy say "upload a sample, not your real certificate".

### Nits

1. The seeded clinics are owned by the admin (`demo-seed.ts:173`). `ClinicScopeGuard` then gives the admin `manage` on all three (`clinic-scope.guard.ts:52`), although its comment says "Admins do not get implicit access" (`:19-20`). In the real flow, the doctor who creates the clinic owns it (`clinics.service.ts:66`). Make the first seeded doctor at each clinic the owner.
2. The placeholder `docKey` `demo/registration-00xx.pdf` (`demo-seed.ts:215`) has no object behind it, so the admin detail for a seeded doctor gives a signed URL that 404s. Write a one-page placeholder through `StorageProvider.putPrivate`, or note it for FE-07.
3. The e2e seed test checks counts only. Add one assertion that each clinic's `staffUserIds` and `staffLog` have length 1 after two runs (probe B shows they do), so a later change to the guarded `$push` cannot duplicate them silently.
