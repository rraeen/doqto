Access-control points checked (D):

- **No `@Roles('doctor')` on `/doctor/*`.** This is safe. The only way to get a profile is `POST /doctor/onboarding`, which uses the caller's own id (`doctors.service.ts:61`). There is no route or field that sets another user's `userId`, and the onboarding DTO rejects `userId` (probe). The `doctor` role is added only to the caller. Self-onboarding is the designed flow, and a new profile is `pending` and unlisted until an admin approves it. So the role grants nothing public. A patient without a profile gets 404 on every `/doctor/*` route (e2e).
- **Photo.** `PUT /doctor/photo` uses `putPublic` with a server-built key (`doctors.service.ts:156-168`), the photo limits (2 MB, JPEG/PNG/WebP, magic bytes) and EXIF stripping (INT-06 should-fix 1, `strip-metadata.ts`). Demo photo URLs depend on `/demo-storage` being public. That is BE-04 Blocker 1. `DemoStorageController` now carries `@Public()`, which that review's round 2 should confirm.
- **Registration change.** Changing council, number or year (`doctors.service.ts:113-125`), or uploading a new document (`:143-148`), calls `resubmit` (`:197-202`), so the profile goes back to `pending`. `saveWithListing` then recomputes `isListed` false (`:186`). The e2e checks the public profile turns 404.
- **Listing in one place.** `computeIsListed` (`listing.ts:21-25`) needs `verified` and nothing `missing`. Every BE-07 write goes through `saveWithListing` except the photo, which cannot change listing. `ratingSummary`, `verification`, `isListed`, `slug` and `slugLocked` are not writable by the doctor (I).

## Findings

### Blockers

None.

### Should fix

1. **`null` passes the DTO for required fields, returns 500 and can corrupt the profile.** `@IsOptional()` lets `null` through as well as `undefined`. The service then tests `!== undefined` (`doctors.service.ts:104-113`). The Zod schema rejects `null` for these fields (`packages/shared/src/doctors.ts`, `name`/`languages`/`qualifications`/`specialties`/`registration` are `.optional()`, not `.nullable()`). The DTO does not (`dto/doctor.dto.ts:89`, `:100-121`, `:143-147`). Failure scenarios (probe):
   - `PATCH { specialties: null }` or `{ qualifications: null }`: the API answers 500, the null is still saved, and from then on `GET` and `PATCH /doctor/profile` return 500. The doctor is locked out of their own profile until someone edits the database.
   - On a listed doctor, `{ qualifications: null }` leaves `isListed: true` with no qualifications. That breaks the "listed means complete" rule in `listing.ts`.
   - `{ name: null }` and `{ registration: null }` return 500 (Mongoose validation and `TypeError` at `:116`). `{ languages: null }` returns 200 and stores `null`, which breaks `DoctorPrivateProfileSchema.languages` (an array).

   This also breaks checklist B ("400 validation"). The DTO comment says a parity test guards this: `// Mirror packages/shared doctors.ts (checked by doctor-dto-parity.spec.ts)` (`dto/doctor.dto.ts:31`). That spec does not exist. Only `src/auth/dto/contract-parity.spec.ts` exists, and the same is true of `clinic-dto-parity.spec.ts` (`clinics/dto/clinic.dto.ts:26`, BE-08 Should fix 4).
   - Fix: replace `@IsOptional()` with `@ValidateIf((_o, v) => v !== undefined)` (rejects `null`) on every non-nullable PATCH field.
   - Add `doctor-dto-parity.spec.ts` like the auth one, feeding the same accept/reject cases (including each `null`) to the Zod schema and the DTO.
   - Add `{ specialties: null }` and `{ name: null }` to the e2e trust-field loop.
2. **A verified doctor can change their name and stay verified and listed.** `updateOwn` writes `name` (`doctors.service.ts:104`) but calls `resubmit` only for registration changes (`:113-125`). The admin checks the registration against the name on the council register. Failure scenario (probe): a verified doctor sets `name: 'Devi Prasad Shetty'`. The profile stays `verified` and listed, and search and the public profile show a well-known doctor's name with the "verified" badge, on a registration issued to someone else. The slug is locked, so the URL keeps the old name. Fix: when the profile is `verified` (or `pending` with a document), treat a `name` change like a registration change: `resubmit(d)`. Or allow only small edits (for example the same name after `normalize`, trim and case) without review. Add an e2e. Note it in the BE status file so FE-05 can warn the doctor before saving.
3. **Onboarding and the role grant are two separate writes.** `doctors.create` (`:60`) and then `users.updateOne($addToSet roles)` (`:83`). If the second write fails (connection drop, process restart), the doctor exists without the `doctor` role. A retry then gets 409 (`:50`), so nothing ever adds the role. Today nothing reads the role for `/doctor/*`, but BE-13 onwards and `/me` will. Fix: in `requireOwn` (or on the 409 path), re-run the idempotent `$addToSet` when the role is missing. Or add the role first, since an extra role with no profile grants nothing.
4. **Old registration scans are never deleted.** Every upload writes a new private key (`:137`), and the old `docKey` is overwritten without deleting the object (`StorageProvider` has no delete, per the BE status note). Credential scans are personal data. DB doc section 6 retention and BE-42 deletion need to find all of them, not only the latest. Fix: record superseded keys (`registration.previousDocKeys` or a small `storageGarbage` collection) so a later cleanup job or BE-42 can remove them. Ask INT for `delete(key)` in `StorageProvider` (see Requests).

### Nits

1. **A slug collision is reported as "already onboarded".** `onboard` maps any 11000 to "You have already started onboarding" (`doctors.service.ts:73-80`). Two different users with the same name onboarding at the same moment both pass `uniqueSlug`, and the second hits the unique `slug` index (probe: 409 with that message, no profile created). Check `keyPattern.slug` and retry `uniqueSlug` once. The same race in `saveWithListing` (`:183`) surfaces as a 500.
2. `EXT[file.mimetype] ?? 'bin'` (`:134`, `:160`) can never reach `'bin'`, because the provider already rejects other types. Use `EXTENSION_BY_TYPE` from `integrations/storage/upload-limits.ts` so the two lists cannot drift.
3. The controller comment (`doctor-profile.controller.ts:36-40`) is the only place that explains why `/doctor/*` has no `@Roles`. Repeat it in `CONTRACT.md` ("any logged-in user; 404 until onboarded"), so the next reviewer does not add `@Roles('doctor')` and break the first session after onboarding.
