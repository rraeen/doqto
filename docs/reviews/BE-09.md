## Findings

### Blockers

1. **A decision is not tied to the state the admin reviewed, and the save loses concurrent writes.** `decide` loads the doctor (`admin-doctors.service.ts:142`), changes `verification` in memory (`:151-154`) and calls `saveWithListing` (`:155`). That is a Mongoose `save()`, which writes only the paths that changed in this copy (`doctors.service.ts:174-189`). The doctor schema has no version check on save. Failure scenarios, both reproduced (probe):
   - **P1, no race needed.** An admin opens a pending doctor, checks registration `N-9` against the council site, and clicks approve. In the minutes in between, the doctor changed the number (or uploaded a different scan). `resubmit` sets `pending` again, but the doctor was already `pending`, so the admin's approve still goes through. The doctor is verified and listed on a registration and document the admin never saw. The audit log cannot show this, because it does not record what was approved (Should fix 1). A verified badge on an unreviewed registration defeats the point of the story.
   - **P2, two admins (or a double click).** Approve and reject run in parallel. Each loads `pending / isListed false`. The approve writes `verified, isListed true`. The reject writes `status: 'rejected'`, but its computed `isListed` (false) equals the value it loaded, so Mongoose does not write it. Final: **`rejected` and `isListed: true`**. A rejected doctor is in public search and bookable, and both audit rows say `before: pending`. The same lost update happens between an admin decision and a doctor's own `PATCH` or a clinic address change (`refreshListingById`, `clinics.service.ts:111`), which all go through the same `saveWithListing`.

   This fails the "approve or reject" criterion: a reject that leaves the doctor listed has not taken effect, and an approval no longer means "an admin checked this registration". Fix (all three parts):
   - **Optimistic concurrency on doctors.** Set `optimisticConcurrency: true` in `doctor.schema.ts`, so every `save()` checks and bumps `__v`. Map `VersionError` to `409 CONFLICT` ("The profile changed, reload"). This closes P2 and the doctor-PATCH/clinic-address races in one place. `saveWithListing` should also always mark `isListed` as modified, so the stored value is always the one just computed.
   - **Bind the decision to what was reviewed.** Add `expectedSubmittedAt` (or a `reviewToken` = `submittedAt` + `docKey` hash returned by the detail) to `VerifyDoctorRequest` (`packages/shared/src/admin.ts`). Make the update conditional, `{ _id, 'verification.status': 'pending', 'verification.submittedAt': expected }`, and answer 409 when it does not match. A decision on an already decided doctor should also get 409, unless a separate "revoke" action is defined, with its own audit action.
   - **Tests.** Add an e2e for P1 (PATCH between detail and approve gives 409) and for P2 (parallel approve + reject: exactly one 200, the other 409, and `isListed` matches the status). Add CONFLICT to `CONTRACT.md` (this also closes BE-05 Should fix 2).

### Should fix

1. **The audit log does not say what was approved.** `before`/`after` hold only `status`, `isListed` and `notes` (`admin-doctors.service.ts:150`, `:156-163`). After the fact (a complaint, a council query), nobody can tell which registration number, council, year or document version the admin accepted. The live document can change later, and old scans are not kept by key (BE-07 Should fix 4). Fix: put `registration { council, number, year }`, `docKey` and `submittedAt` into `after` (or a `subject` field). These are not patient data and not secrets. `docKey` is useless without a signed URL.
2. **The queue sorts by account age, not by submission.** The sort is `createdAt` (`:82`), but the item shows `submittedAt` (`:105`). A doctor who resubmits today after a rejection months ago is placed by their sign-up date, ahead of first-time doctors who have waited longer. For an "oldest first" queue, sort and paginate on `verification.submittedAt` (and add `{ 'verification.status': 1, 'verification.submittedAt': 1, _id: 1 }` to the migration), or say in `CONTRACT.md` that the order is by sign-up.

### Nits

1. **Use the 5-minute TTL on this route explicitly.** `detail` uses the global `SIGNED_URL_TTL_SECONDS` (`:114`), which an operator can raise to an hour for some other use. Checklist E says scans are served "only through 5-minute signed URLs". Pass `Math.min(300, config)` here.
2. **Viewing a scan is not audited.** Checklist D asks for an audit row on every admin *action*. `GET /admin/doctors/:id` mints a credential link without one. One `doctor.document.view` row per detail call costs little and records who looked at a doctor's ID document (DPDP access trail).
3. Approval notes are stored in `verification.notes` and shown to the doctor (`doctor.mappers.ts:67-71`). That is fine, but FE-07 should say so next to the notes field, so an admin does not write internal remarks there.
4. `phone: ''` when the user row is missing (`:95`, `:120`) breaks the E.164 promise of `AdminDoctorQueueItemSchema`. Use `null` (contract change), or skip the row and log it.
