Other focus points checked:

- **Trust (I, ADR 0008).** `doctors/` and `ranking/` import nothing from `payments` or `subscriptions` (grep). `ratingSummary` is written only by the rating job (`doctor.schema.ts`). `overall()` (`doctor-search.service.ts:145-147`) is the "Bayesian score" input that TDD 5.8 asks for. It feeds ranking only and is never returned: no list or profile key carries it, which matches TDD 5.4 and design-doc-differences row 4.
- **$geoNear.** It is the first stage (`:67-74`). `near` is `[lng, lat]` (`:69`), `maxDistance` is in metres with `spherical: true` (`:71-72`), and it uses the `clinics.location` 2dsphere index (`clinic.schema.ts:63`), which the startup migration `0002-sprint2-doctor-clinic-indexes` creates. e2e checks `distanceMeters <= 10000` and nearest first.
- **City.** It is stored lowercase from the primary clinic (`doctors.service.ts:178`) and matched with trim and lowercase (`doctor-search.service.ts:82`). The `{ isListed, city, specialties }` index (`doctor.schema.ts:100`) fits this query.
- **Injection (C).** The DTO validates every query field (`search.dto.ts`), and nested objects get 400. `q` is escaped (`:47`, `:84`) and limited to 2 to 60 characters. `specialty` is `@IsIn(SPECIALTY_KEYS)`. The slug is checked against `^[a-z0-9-]{3,90}$` before any query (`doctors.controller.ts:38`).
- **Cursor and limits (B).** The cursor is an opaque offset, rejected unless it is an integer from 0 to 500 (`doctor-search.service.ts:34-45`). Forging it can only move within the same capped list. `limit` is 1 to `PAGE_LIMIT_MAX` in the DTO and capped again in the service (`:59`).
- **Public and throttling (D).** `@Public()` is on the controller (`doctors.controller.ts:10`). The global `ThrottlerGuard` (`app.module.ts:64`, 100 requests per 60 s by default) still applies because `@SkipThrottle` is absent.
- **Privacy (E, J).** No doctor phone, registration, `docKey`, `userId`, staff, audit or verification notes in any public shape (probe keys above). The e2e also checks that the registration number and the doctor's phone are not in the body. The clinic `phone` is the clinic's public number from the contract (`ClinicSchema`). No clinical fields.
- **Contract (B, M).** Both routes are in `CONTRACT.md` (rows 94 and 95) and in Swagger (`@ApiTags('doctors')`).

## Findings

### Blockers

None.

### Should fix

1. **The search service is outside the `no-payments-in-trust-code` rule.** The ESLint block (`eslint.config.mjs:64-75`) covers `reviews/**`, `ranking/**`, `search/**` and `*ranking*` files. Search lives in `apps/api/src/doctors/doctor-search.service.ts`, and `--print-config` confirms that file gets no `doqto/no-payments-in-trust-code`. That file builds the `RankingInput` (`:114-120`: score, review count, distance). Example failure: a later change adds `availability` or a "boost" from a `payments`/`subscriptions` import there, and CI stays green, which breaks the guarantee TDD 5.8 and ADR 0008 rely on ("Enforced with an ESLint import-boundary rule in CI"). There is no violation today. Fix, either:
   - **BE:** move `DoctorSearchService` into `apps/api/src/search/`, which is already covered (preferred, no INT change); or
   - **INT:** add `apps/api/src/doctors/doctor-search*.{ts,js,mts,cts}` to the rule's `files` (see Requests).
2. **An out-of-range `near` returns 500 instead of 400.** The DTO regex (`dto/search.dto.ts:37`, mirrored in `packages/shared/src/doctors.ts:199-202`) accepts any 1-2 digit latitude and 1-3 digit longitude. `doctors.controller.ts:23,27` passes them straight to `$geoNear`. `GET /doctors?near=95.0,79.4` and `?near=28.0,999` return `500 INTERNAL` (probe), so anyone can produce 5xx noise and error-rate alerts with a public, unauthenticated URL, and checklist B ("400 validation") fails for this input. Fix: after parsing, validate against the contract's `LatLngSchema` (India bounds, lat 6 to 38, lng 68 to 98, `packages/shared/src/clinics.ts:18-21`) in both the Zod schema and the DTO, and return `VALIDATION_FAILED` with `path: 'near'`. Add the two probe cases to the e2e.
3. **A suspended or deleted doctor account stays public.** Both queries filter only on `doctors.isListed` (`doctor-search.service.ts:63`, `:136`), and `computeIsListed` (`listing.ts:21-25`) knows nothing about `users.status`. In the probe, setting the seeded doctor's user to `status: 'suspended'` left the profile at 200 and the doctor in search. No API suspends or deletes users yet, so nothing is exposed today. But the first suspension (admin action or BE-42 deletion) will keep the doctor bookable unless someone remembers. Fix, either:
   - make the rule explicit now: whatever sets `users.status` to `suspended` or `deleted` must also set `isListed: false`, written in the BE status file as a requirement for the story that adds suspension and for BE-42; or
   - add `listingBlocked` to the doctor and include it in `computeIsListed`.
   Add an e2e for the 404 when that path lands.

### Nits

1. **Which 500 candidates get ranked is arbitrary.** `this.doctors.find(filter).limit(MAX_CANDIDATES)` (`doctor-search.service.ts:86`) has no sort. Once a query matches more than 500 doctors, which 500 are ranked can change between page requests, so the offset cursor can skip or repeat doctors. Doctors past 500 are never reachable. This is harmless at Phase 1 scale (tens per city). Add `.sort({ _id: 1 })` and a comment, or log when the cap is hit. The offset cursor also shifts when a doctor is listed or unlisted between pages. That is acceptable, but say so in `CONTRACT.md`.
2. **The near-search candidate pool includes clinics with no listed doctor.** `$geoNear` takes the 500 nearest clinics (`:75`) before the listed filter, so clinics with no listed doctor use up candidate slots. Adding `query: { doctorIds: { $ne: [] } }` to the `$geoNear` stage keeps the pool to clinics that can produce a result. Not needed at pilot scale.
3. **City search only matches the primary clinic's city.** `filter.city` uses the city of the doctor's first clinic (DB doc 3.2). A doctor whose second clinic is in Bareilly does not appear for `city=bareilly`, though they do appear for `near=`. This matches the DB doc. Add a one-line note in the BE status file so FE does not report it as a bug.
4. **`overall()` (`:145`) needs a clearer name.** Rename it to something like `rankingScore()`, with a comment that it must never be returned. design-doc-differences row 4 removed `overall` precisely so that no single score gets shown (TDD 5.4).
5. **`specialtyMatch` is always true here.** `filter.specialties` already restricts the results to the specialty (`:83`, `:116`). That is fine and keeps the input honest for a later "related specialties" search, but a comment would stop someone from deleting the field as dead.
